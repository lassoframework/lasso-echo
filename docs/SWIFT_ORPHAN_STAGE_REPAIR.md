# Swift orphan staged-use maintenance

This offline-prepared utility is limited to Swift River's three exact asset/date/staged-time identities hardcoded in `tools/swift_orphan_stage_repair.py`. It is not a general rollback or a production repair receipt. No live state was mutated during implementation.

Run from the repository root with `python3 -m tools.swift_orphan_stage_repair --plan /absolute/frozen-plan.json --db /absolute/echo.db`. Default mode opens an existing SQLite database read-only, validates the supplied frozen plan and compares exact raw ledger strings. It makes no network calls and creates no journal, lock, or database. A passing dry run only establishes offline preparation, not current Supabase state or a verified fence.

The plan JSON has `schema: 1`, `gym_id: "swiftrivercrossfite5c9db"`, and exactly three `entries`. Each entry requires the exact `key`, `ledger_before` raw string, `source_before` full media_source row, and `asset` frozen row containing all `PINS` fields. `content_hash` and `drive_modified` must both be nonempty. `source_before` must be active, own-tenant and match `source_id`. Counters must be exactly 1 and last-used must match the authorized staged instant. The exact ledger record must say previous counter 0, previous last-used null, rolled_back false, and match the authorized identity. Freeze current source versions first; historical summary values cannot fill these fields.

Before an attended apply, a separate operator must establish and independently verify a real fence over every relevant writer. Stopping a single worker or taking a SQLite transaction does not fence portal, Drive sync, scripts, provider queues or another replica. Collect tenant-scoped evidence of no current owners, leases, queued writes, unknown/in-flight sends, matching calendar rows, posts, audit, served or ops receipts. Absence from a prior query is insufficient. Reconcile every unknown provider request before proceeding. Keep the fence held across partial failure and resume. The tool does not establish a fence, authenticate an operator signature or independently inspect provider queues; it consumes the operator's attestation, so the operator must verify and retain its underlying receipts.

Supply a reviewed fence receipt containing:

- `plan_sha256` returned by dry run, exact `gym_id`, durable `fence_id`, `verified_by`, and independently verified, still-held fence booleans `independently_verified`, `fence_held`, `retain_until_journal_complete` all true.
- `verified_at` and `expires_at` as UTC timestamps covering an attended window no longer than 15 minutes. Refresh evidence under the same continuously held fence to resume after expiration.
- `writers` covering every identifier in `WRITERS`; `other_relevant_writers: []` attests no unlisted relevant writer remains unfenced.
- Empty arrays for every identifier in `CLEAR`. These are reviewed absence assertions backed by operator receipts, not values automatically inferred by this utility.

Only with authorized maintenance, append `--apply --fence-receipt /absolute/reviewed-fence.json --journal /durable/private/path/journal.json`. The journal parent must already exist. Use durable storage with restrictive directory permissions. Supabase credentials are loaded through the existing configuration only after plan/fence validation and are never included in the journal. The existing Supabase `update_asset` method is ID-only and is never used. The adapter sends one atomic PostgREST PATCH with tenant, asset, source ID, content hash, Drive modified version, counter, last-used and approval/eligibility predicates, requires exactly one returned row, then independently reads the asset again. Any rejected/unavailable predicate/API blocks; there is no weaker fallback. Source row ownership/full before-image is checked before and after while the operator fence protects cross-table changes. There is no cross-store distributed transaction.

The tool prechecks all three assets, sources and whole date ledgers before recording any intent. Each asset's intent is atomically replaced and fsynced before remote mutation. The target counter becomes exactly 0 and last-used becomes null; an exact after-image readback during durable resume prevents double decrement after a lost response. Fence freshness is rechecked immediately after source/asset reads and journal fsync before the remote CAS, after SQLite lock acquisition, immediately before the SQLite update and before commit. Expiration rolls back an uncommitted ledger transaction while retaining any previously committed remote half and durable intent for fenced resume. SQLite uses BEGIN IMMEDIATE and a raw whole-ledger value comparison, changes only the matching record's rolled_back field, preserves every sibling record and field, commits and reads back. Joint final readback occurs under the still-held fence. The journal binds the complete frozen plan and fence ID; a different plan or fence cannot silently adopt it.

On any failure, retain the fence and the original plan, journal, DB and remote receipts. Do not call legacy rollback, edit the ledger by hand, start another journal, or release writers based on a partial journal. Resume only with renewed verification under the original continuously held fence. A complete journal requires independent operator verification of both sides before external fence release; the tool never releases a fence or claims provider delivery, publication or support-ticket closure.

Offline targeted tests cover stale counters/source versions/ownership, changed ledgers, active owners and unknown sends, lost response resume, repeat idempotence, sibling preservation, partial conflict, fence mismatch and exact atomic predicate construction. Live PostgREST compatibility and real fence effectiveness remain operator acceptance prerequisites.
